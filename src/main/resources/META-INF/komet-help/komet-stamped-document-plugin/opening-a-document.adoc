= Opening an AsciiDoc document

The card reads documents from git, and from folders without git.
Opening a file in git materializes its history: each commit that touched the file is written into the knowledge base, so every line can name the commit that introduced it.

== Before you start

* Komet has a store open. A memory-only store works, but forgets the document when Komet quits; see xref:stores.adoc[Persistent and memory-only stores].
* The file is an `.adoc` file. In a git working tree it is committed, and the card reads the file as it is. Changes saved in the file and not yet committed show as an edit that is not committed, written by you, which the bar at the bottom of the card offers to commit. A change to the document's title, its attributes or a section heading is not shown that way: the card then shows the last commit and says why.
* A file in a folder without git is read as one version, because an ordinary file has no history. Every line has the same STAMP: the time the file was last changed, and you as its author. Such a file has no history and no narration, and Save keeps your edits, since there is nothing to commit them to. *More › Start Git History* makes the folder a git repository, with the file as its first commit, and reads the document in again from git.

== Open the file

. In the card's toolbar, open the *More* menu and choose *Open file…*.
. Choose the `.adoc` file. The chooser starts in the working tree you used last.
. Wait while the card materializes the file. A file that includes other files is materialized with every file it includes, each as its own document, in include order. A bar at the top of the card counts the files, for example _Materializing 12 of 51_, and names the file being written. A long history takes a while the first time. Opening the file again writes only the commits the knowledge base lacks.
. The document appears in the document chooser and on the card.

=== Pause or stop a long run

While the bar shows, *Pause* waits after the file being written, and *Resume* goes on with the next one.
*Stop* keeps the files already written and leaves the rest as they are.
The card then opens the document. An included file the knowledge base does not hold yet shows as its include line.
The link under the report, for example _Show the 46 files_, lists the files the run did not reach. Open the file again to materialize the rest.

An include that names a file the card cannot find is listed in the same place, with its line and the reason.
The run goes on without it.

When a document is read in, Komet gives it a module of its own, named for its folder and path.
That module is a kind of _File module_, so the document is local data saved in a file: the file and its git history contain all of it, and the knowledge base keeps a copy only while Komet is open.
xref:kinds-of-data.adoc[Kinds of data] explains what that means and how it differs from knowledge and shared data.

== Open it again later

While Komet is open, a document stays in the knowledge base: choose it in the document chooser.
When new commits have reached the file, choose *More › Materialize* to write them.

When a knowledge base opens, Komet removes the copies of documents saved in files, because each file is its document's record.
After a restart, open the file again, from the Documents tray or with *Open file…*, and its history is read in again.
A document whose edit was never saved, because Komet stopped first, is kept, and its card asks what to do with the edit; see xref:stamped-document.adoc[the card overview].

== Choose how to read it

Use the views in the toolbar: *Reading* for the document as written, *Source* for its lines and their STAMPs, *Page layout* for its pages, and *Graph* for how the knowledge base holds it.
The xref:stamped-document.adoc[card overview] describes each control.

== If something goes wrong

_Cannot read the file at HEAD_:: The file has not been committed yet. Commit it, then open it again.
_The document classifies as knowledge_:: The store was made before the File module existed. Load the current starter set into the store, then materialize the file again.
